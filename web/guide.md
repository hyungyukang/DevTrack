# DevTrack 사용 방법

처음 쓰는 분이 **위에서부터 차례로 따라 하면** 바로 쓸 수 있도록 정리한 매뉴얼입니다.
1~5단계는 처음 한 번만 하는 준비이고, 6단계부터가 매일 쓰는 방법입니다.

## 0. DevTrack 이란?

Claude 같은 AI 에게 일을 맡기고, **무엇을 하고 있는지 · 어디서 막혔는지 · 결과물이 무엇인지**를 웹에서 확인하는 도구입니다.
저장소에 커밋하거나 PR 에 코멘트를 다는 일처럼 되돌리기 어려운 일은 **웹에서 승인해야만** 진행됩니다.

```text
 ① 사용자: 작업 지시  ──▶  ② Claude: 작업하면서 DevTrack 에 기록
                               (지금 하는 일 · 문제 · 결과물 · 승인 요청)
 ④ 사용자: 승인 / 수정 요청  ◀──  ③ 웹 대시보드: 진행 상황 · 알림
          │
          └──▶ ⑤ Claude: 승인된 내용만 커밋 · 푸시 · 게시
```

자주 나오는 말:

| 용어 | 뜻 |
|---|---|
| 작업 (`T-0001`) | 맡긴 일 하나. 지시 내용, 계획, 진행 기록, 문제, 결과물, 승인 요청이 모두 여기에 모입니다 |
| 단계 · 진행률 | Claude 가 "지금 하는 일"을 적을 때마다 갱신됩니다 |
| 문제 (`I-1`) | 작업 중 발견한 문제나 막힌 점 |
| 결과물 (`F-1`) | 리포트, 그림, 코드 변경(diff), 논문 PDF, 노트북 등 — 웹에서 바로 열어 볼 수 있습니다 |
| 승인 요청 (`A-1`) | Claude 가 다음으로 넘어가기 전에 확인을 구하는 것. **승인 · 수정 요청 · 거절** 중 하나로 답합니다 |

## 1. 준비물 확인

터미널에서 아래 명령이 모두 실행되는지 확인합니다.

```bash
python3 --version      # 3.7 이상 (HPC 에서는 module load python 등)
git --version
```

- **Claude Code** — VS Code 확장 또는 터미널용 `claude` 명령. AI 가 일하는 곳입니다.
- **GitHub CLI (`gh`)** — 코드 리뷰를 맡길 때만 필요합니다. `gh auth status` 로 로그인되어 있는지 확인하세요.

DevTrack 은 Python 표준 라이브러리만 쓰므로 `pip install` 같은 설치 과정이 없습니다.

## 2. DevTrack 내려받기

```bash
git clone git@github.com:hyungyukang/DevTrack.git ~/devtrack
```

이후 설명은 `~/devtrack` 에 받았다고 가정합니다. 다른 곳에 받았다면 경로만 바꿔 주세요.

## 3. `devtrack` 명령 등록 (PATH)

어느 폴더에서든, 그리고 **Claude 도** `devtrack` 명령을 쓸 수 있게 셸 설정 파일에 경로를 추가합니다.

```bash
echo 'export PATH="$HOME/devtrack/bin:$PATH"' >> ~/.zshrc     # bash 를 쓰면 ~/.bashrc
source ~/.zshrc
devtrack --version                                           # → devtrack 0.1.0
```

기록은 기본으로 `~/devtrack/data/` 에 저장됩니다. 다른 곳에 두려면 `devtrack config data ~/devtrack-data` 를 한 번 실행하세요.
설정 파일(`~/.config/devtrack/config.json`)에 저장되어, 어느 터미널 · 프로그램에서 실행한 devtrack 이든 같은 곳에 기록합니다.
지금 쓰는 곳은 `devtrack config` 로 봅니다.
`export DEVTRACK_DATA=…` 로도 정할 수 있지만, 그 변수가 없는 곳에서 실행된 devtrack 은 기본 폴더에 기록합니다.
변수를 정하기 전에 연 터미널, VS Code 의 Claude 와 훅이 그런 예입니다.

## 4. 웹 대시보드 열기

```bash
devtrack serve --open          # → http://localhost:8765
```

- 이 터미널 창은 **열어 둔 채로** 두세요. 닫으면 웹이 꺼집니다.
- 화면 오른쪽 위에 **실시간 · 로컬 서버** 가 보이면 정상입니다. 이 모드에서는 웹에서 누른 승인 · 지시가 바로 저장됩니다.
- 처음에는 작업이 없어 빈 화면입니다. 예시를 먼저 보고 싶다면 → [12. 자주 묻는 질문](#/guide/s12)의 "예시 화면".
- 처음 열면 **영어 화면**입니다. 오른쪽 위 **한** 단추를 누르면 한국어로 바뀌고, 고른 언어는 브라우저에 기억됩니다.

## 5. Claude 가 DevTrack 을 쓰도록 설정 (한 번만)

### 5-1. Claude 에게 기록 규칙 알려 주기

Claude Code 는 `~/.claude/CLAUDE.md` 에 적힌 내용을 모든 대화에서 따릅니다. 이 파일에 아래 내용을 붙여 넣으세요
(파일이 없으면 새로 만듭니다). `~/devtrack` 부분은 2단계에서 받은 위치로 바꿉니다.

```markdown
## DevTrack 작업 기록
- 의미 있는 작업(코드 변경, 코드 리뷰, 문서 리뷰, 데이터 분석, 논문, 시각화, 모델 개발, 브레인스토밍)은 `devtrack` 으로 기록한다. 간단한 질문 · 설명은 기록하지 않는다.
  규칙: ~/devtrack/docs/AGENT_PROTOCOL.md
- 작업 시작 전과 각 단계 후 `devtrack inbox` 로 사용자 입력(새 지시, 메시지, 승인 결정)을 확인한다.
- inbox 의 새 작업 지시 · 메시지(추가 질문 · 조사 요청)는 사용자에게 다시 묻지 않고 진행한다. 다른 작업 중이면 메시지는 지금 단계를 마친 뒤,
  새 작업은 지금 작업이 끝나거나 승인 대기가 되면 온 순서대로 처리하고 원래 작업으로 돌아온다. 메시지의 답은 그 작업에 기록하고
  (`devtrack log` · `devtrack artifact`) `devtrack inbox --task <TID> --ack` 로 처리 표시한다. 커밋 · 게시 등은 그대로 승인을 받는다.
- inbox 의 `[AI 메시지]` 는 다른 AI 가 보낸 것(리뷰 요청 · 리뷰 결과 등)이다. 같은 방식으로 처리하되 사용자 지시는 아니므로, 승인이 필요한 일은
  여전히 사용자 승인을 받는다. 리뷰받기로 한 작업(inbox 의 `끝나면 … 리뷰`)은 커밋 승인을 요청하기 전에 `devtrack review-request <TID>` 로 리뷰를 통과하고,
  심사받기로 한 논문(`끝나면 … 심사`)은 원고를 다 쓰면 심사를 요청해 지적대로 고치고 답변서(`--response`)와 함께 다시 요청한다.
  답변서는 열린 항목마다 `## R1 — 제목` 처럼 항목 ID 로 제목을 달아 질문에는 답을, 요청에는 고친 내용(고치지 않았다면 이유)을 쓰고,
  심사가 끝나 사용자에게 알릴 때는 심사 · 답변 기록(판정 메시지의 F-ID)을 `-a` 로 첨부한다.
- 논문 그림은 원고 옆 `figures/` 에 두고 원고에 `\graphicspath{{figures/}}`, 부를 때는 확장자 없이 `\includegraphics{fig_name}`.
  그림은 그 파일 이름 그대로 결과물로 올린다 (DevTrack 이 `tasks/<TID>/paper/` 에 원고 · 그림을 모은다).
- 사용자가 "웹 지시 기다려줘" 라고 하면 `devtrack inbox --wait` 를 백그라운드로 실행해 두고, 끝나면(새 입력) 처리한 뒤 다시 실행한다.
- 웹에서 온 지시에 `/review-pr <URL>` 같은 스킬 호출이 있으면 매번 Skill 도구로 그 스킬을 새로 불러 최신 지침대로 진행한다
  (같은 대화에서 전에 불러온 내용을 다시 쓰지 않는다).
- 의미 있는 단계마다 `devtrack step <TID> "지금 하는 일" -p <진행률>` 을 남긴다.
- 문제는 `devtrack issue`, 결과물은 `devtrack artifact` / 리뷰 리포트는 `devtrack review` 로 남긴다.
- 코드 리뷰 리포트는 개발자가 아닌 사람도 이해할 수 있게 쓴다: 한 줄 결론, 비개발자용 "한눈에 보기", 항목별 "쉽게 말하면", 용어 풀이.
- DevTrack 작업의 결과를 저장소에 반영할 때는 git commit/push 를 직접 하지 않고 `devtrack request <TID> "..." --commit -m "..."` 로
  승인을 요청하고, 승인되면 `devtrack apply <TID> <AID>` 로 반영한다. 단, 사용자가 채팅에서 직접 커밋 · 푸시를 지시하면 따른다.
- 사용자가 `[DevTrack 결정]` / `[DevTrack 메시지]` / `[DevTrack 새 작업 지시]` / `[DevTrack 작업 완료]` / `[DevTrack 작업 취소]` / `[DevTrack 작업 삭제]`
  메시지를 보내면 각각 `devtrack decide` / `devtrack comment` / `devtrack new` / `devtrack done --by-user` / `devtrack cancel` /
  `devtrack delete --yes` 로 먼저 기록한 뒤 진행한다.
- inbox 에 `[완료 처리]` · `[취소]` · `[삭제]` 가 오거나 도구 실행이 `⛔ DevTrack` 메시지로 막히면 그 작업은 즉시 멈추고, 안내대로 확인만 기록한 뒤
  (`devtrack inbox --task <TID> --ack`) 더 기록하지 않는다. 작업 삭제는 사용자가 요청하고 확인했을 때만 한다.
```

> 설정은 **새로 연 Claude 대화부터** 적용됩니다. 이미 열려 있는 대화는 새로 시작하세요.

### 5-2. 리뷰 스킬 설치 (코드 · 문서 리뷰를 맡길 경우)

`/review-pr` 스킬이 DevTrack 에 코드 리뷰 결과를 올리고, 웹에서 코멘트할 항목을 고를 수 있게 해 줍니다.
`/review-doc` 스킬은 논문 · 보고서 · 제안서(PDF · Word · LaTeX)를 리뷰해 요약과 고칠 부분을 PDF 리포트로 올립니다 ([문서 리뷰](#/guide/s9)).

```bash
mkdir -p ~/.claude/skills/review-pr ~/.claude/skills/review-doc
ln -sf ~/devtrack/integrations/claude-skills/review-pr/SKILL.md ~/.claude/skills/review-pr/SKILL.md
ln -sf ~/devtrack/integrations/claude-skills/review-doc/SKILL.md ~/.claude/skills/review-doc/SKILL.md
```

복사 대신 링크로 걸어 두면 `git pull` 만으로 스킬도 함께 최신이 됩니다.
리뷰 리포트를 메일로 받는 기능은 `pr-review-report` 스킬이 함께 설치되어 있어야 합니다
([자세히](https://github.com/hyungyukang/DevTrack/tree/main/integrations/claude-skills)).

### 5-3. 권한 확인 창 줄이기 (선택)

Claude 가 `devtrack` 명령을 실행할 때마다 확인 창이 뜨면, Claude Code 에서 `/permissions` 를 열어 허용 규칙
`Bash(devtrack:*)` 를 추가하세요. `devtrack` 은 기록만 하고, 커밋 · 푸시는 웹에서 승인된 요청만 실행합니다.

### 5-4. 작업 취소를 바로 전달하기 (권장)

Claude 는 작업 단계가 끝날 때만 DevTrack 을 확인합니다. 그래서 작업 도중에 웹에서 취소 · 삭제해도 그 단계가 끝날 때까지
계속 일할 수 있습니다. **훅**을 설치하면 Claude 가 명령을 실행하거나 파일을 고치기 **직전마다** DevTrack 이 "이 작업이
취소됐는지" 확인하고, 취소됐으면 그 동작을 막고 멈추게 합니다.

`~/.claude/settings.json` 에 추가합니다. 파일이 없으면 새로 만들고, 이미 `"hooks"` 가 있으면 그 안의 `"PreToolUse"` 목록에
항목만 더합니다. `/Users/me/devtrack` 은 2단계에서 받은 위치의 **전체 경로**로 바꿉니다.

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "hooks": [
          { "type": "command", "command": "/Users/me/devtrack/bin/devtrack-hook", "timeout": 10 }
        ]
      }
    ]
  }
}
```

- 훅은 **그 대화가 맡은 작업만** 확인합니다 (한 번에 0.05초 정도). 다른 대화 · 다른 작업에는 영향이 없습니다.
- `devtrack-hook` 은 `devtrack hook` 을 실행하되 문제가 생겨도 Claude 를 막지 않게 만든 실행 파일입니다.
- 막힌 Claude 는 `devtrack inbox --task T-0003 --ack` 로 확인을 기록하고 멈춥니다. 그 뒤로는 평소처럼 동작합니다.
- 설정은 **새로 연 Claude 대화부터** 적용됩니다. Codex 는 11단계 ⑤ 를 보세요.

## 6. 첫 작업 맡기기

방법은 세 가지입니다. 편한 쪽을 쓰면 되고, 어느 쪽이든 결과는 웹에 똑같이 나타납니다.

### 방법 A — Claude 채팅으로 지시

VS Code 의 Claude 채팅창(또는 터미널에서 실행한 `claude`)에 평소처럼 지시합니다.

```
~/project 의 압력 솔버를 HIP 으로 포팅해줘. 검증까지 하고, 커밋은 승인받고 해줘.
```

Claude 가 DevTrack 에 작업(`T-0001`)을 만들고 진행 상황을 기록하기 시작합니다. 웹 대시보드에 바로 나타납니다.

### 방법 B — 웹에서 지시 (대기 모드)

1. Claude 채팅창에 한 번만 이렇게 말해 둡니다. 이 대화(VS Code 창)는 열어 두세요. VS Code 없이 터미널에서 하려면 방법 C 를 보세요.
   ```
   웹 지시 기다려줘
   ```
2. 웹 왼쪽 위 **새 작업 지시** 를 누르고 입력합니다.

   | 칸 | 적을 내용 |
   |---|---|
   | 작업 제목 | 한 줄 요약 (예: `PR #42 코드 리뷰`) |
   | 작업 유형 | 코드 개발 · 코드 리뷰 · 논문 작성 · 문서 리뷰 · 데이터 분석 · 시각화 · AI 모델 · 브레인스토밍 · 기타 — 맞는 메뉴(작업 분야)에 표시됩니다. 문서 리뷰를 고르면 문서 경로 · 종류 · 목적 칸으로 바뀝니다 ([9단계](#/guide/s9)) |
   | 담당 AI · 우선순위 | 이 작업을 처리할 AI — 그 AI 만 가져갑니다 (Codex 는 [11단계](#/guide/s11)). 바로 아래에 지금 웹 지시를 기다리는 AI 가 표시됩니다 |
   | 모델 · 추론 강도 | 이 작업을 처리할 AI 모델과 강도 (선택, 예: Opus 5.5 · Extra high) — 정하면 그 모델로만 처리합니다 ([6-1](#/guide/s6-1)) |
   | 대상 저장소 경로 · 브랜치 | 코드를 고칠 저장소 (선택) |
   | 리뷰 받기 · 심사 받기 | 코드 개발 · 논문 작성일 때만 (선택). 끝나면 다른 AI 에게 리뷰 · 심사를 받게 합니다 ([6-2](#/guide/s6-2), [6-3](#/guide/s6-3)) |
   | 관련 작업 | 예: 이 분석을 쓸 논문 작업 (선택). 목록에서 여러 개를 차례로 고르거나, 옆 칸에 작업 번호를 직접 적습니다 (`T-0001, T-0002` 또는 `1 2`) |
   | 지시 내용 | 목표, 참고 자료, 완료 기준, 승인받아야 할 시점 — 구체적일수록 좋습니다 |

3. **작업 지시 등록** 을 누르면 몇 초 안에 Claude 가 자동으로 작업을 시작합니다.
   작업 화면 위쪽에 담당 AI 가 지금 웹 지시를 기다리는지 표시됩니다 (로컬 서버 모드).
   - **기다리고 있습니다** (초록): 대기 모드의 Claude 나 `devtrack watch` 가 곧 가져갑니다.
   - **기다리는 Claude 가 없습니다** (노랑): 아래 방법으로 깨워 주세요. 표시된 문구를 복사해 채팅에 붙이면 됩니다.
   - **이미 확인하고 시작하지 않았습니다** (노랑): 기다리는 AI 가 이 지시를 이미 봤기 때문에 다시 깨어나지 않습니다.
     채팅에서 "T-0007 진행해줘" 처럼 직접 요청하거나, 실행기를 다시 켜세요.
   - **지정한 모델과 달라 이 작업을 받지 않습니다** (노랑): 작업에 정한 모델과 기다리는 대화의 모델이 다릅니다 — [6-1](#/guide/s6-1).

> 대기 모드를 켜지 않았다면, 웹에서 지시한 뒤 Claude 채팅창에 "devtrack inbox 확인하고 진행해줘" 라고 한 번 말하면 됩니다.
>
> AI 가 다른 작업을 하던 중이면 묻지 않고 이어서 처리합니다 — 작업 화면에 보낸 메시지 · 추가 질문은 지금 단계를 마친 뒤,
> 새 작업은 하던 작업이 끝나거나 승인 대기가 되면 시작합니다.

### 방법 C — 터미널에서 Claude 를 띄워 두고 웹으로 지시 (VS Code 없이)

VS Code 를 열지 않고, 터미널에서 `claude` 를 실행해 둔 채 웹으로만 지시할 수도 있습니다. 방법 B 를 VS Code 대신 터미널에서 하는 것입니다.
터미널용 `claude` 가 없으면 [10-3](#/guide/s10-3) ① 처럼 설치하세요 (내 컴퓨터에서도 같습니다).

1. 터미널을 열고, Claude 가 일할 폴더에서 실행합니다.
   ```bash
   cd ~/project        # Claude 가 주로 일할 폴더
   claude
   ```
2. Claude 가 뜨면 한 번만 이렇게 말합니다.
   ```
   웹 지시 기다려줘
   ```
   Claude 가 `devtrack inbox --wait` 를 백그라운드로 켜 두고 기다립니다. 이 터미널 창은 **닫지 말고** 그대로 두세요.
3. 웹에서 **새 작업 지시** 로 지시합니다 (방법 B 의 2–3). 몇 초 안에 이 터미널의 Claude 가 작업을 시작하고, 끝나면 다시 기다립니다.
   진행 상황 · 승인 요청은 웹에서 보고, 승인도 웹에서 하면 됩니다.

알아 둘 점:
- **권한 확인 창은 이 터미널에 뜹니다.** Claude 가 명령 실행이나 파일 수정을 허락받으려고 기다리는 동안은 웹에서 진행이 멈춘 것처럼 보입니다.
  가끔 터미널을 확인하거나, [5-3](#/guide/s5-3) 처럼 자주 쓰는 명령을 미리 허용해 두세요.
- **일할 폴더:** Claude 는 실행한 폴더 안의 파일을 주로 다룹니다. 다른 폴더의 저장소를 자주 맡긴다면 그 상위 폴더에서 실행하거나, Claude 에서 `/add-dir <폴더>` 로 추가하세요.
- **창을 닫으면 멈춤:** 터미널 창을 닫으면 Claude 도 끝납니다. 창을 닫아도 계속 돌게 하려면 `tmux` 안에서 실행하세요 — [10-4](#/guide/s10-4) 와 같은 방법입니다
  (`tmux new -s claude` → `claude` → "웹 지시 기다려줘" → `Ctrl+b` 를 눌렀다 뗀 뒤 `d`). 컴퓨터가 잠자기에 들어가 있는 동안에는 일하지 않습니다.
- **대기 모드는 한 곳에서만:** VS Code 의 Claude 와 터미널의 Claude 를 둘 다 대기 모드로 두면 같은 지시를 둘 다 받아 함께 시작할 수 있습니다.
- **그만 기다리게 하기:** 터미널의 Claude 에게 "웹 지시 그만 기다려" 라고 하거나, `/exit` 로 Claude 를 끝냅니다.

### 6-1. 작업마다 AI 모델 정하기 (선택)

작업마다 처리할 AI 모델과 추론 강도를 정해 둘 수 있습니다. 예를 들어 어려운 포팅 작업은 **Opus 5.5 · Extra high**,
간단한 정리는 **Sonnet 5.5** 로 정합니다. 정해 둔 작업은 그 모델로만 처리됩니다.

- **정하는 곳:** **새 작업 지시** 의 **모델 (선택)** · **추론 강도** 칸입니다. 이미 만든 작업은 작업 화면 위쪽의 모델 표시
  (예: `Opus 5.5 · Extra high 변경`)를 눌러 바꿉니다. 터미널에서는 `devtrack model T-0001 opus-5.5 --effort xhigh` 로 정하고, `--clear` 로 해제합니다.
- **모델 목록**은 담당 AI 에 맞게 나옵니다. Claude 는 Claude 모델, Codex 는 이 컴퓨터의 Codex 가 받아 둔 모델 목록
  (`~/.codex/models_cache.json` — Codex 를 한 번 실행하면 생기고, 없으면 기본 목록), **누구나** 는 둘 다입니다.
  목록에 없는 모델은 **직접 입력…** 을 고르고 이름을 적습니다.
- **추론 강도**는 고른 모델이 받는 값만 나옵니다. Claude 는 Low – Max, Codex 는 모델마다 다르며 지금 모델은 Low – Ultra 입니다.
  모델이 받지 않는 강도는 저장할 때 막습니다. 터미널에서는 `devtrack model --list` 로 고를 수 있는 모델과 강도를 봅니다.
- 비워 두면 지금처럼 어떤 모델이든 처리합니다.

**실행기로 받기 (가장 확실한 방법).** 실행기는 작업을 실행할 때마다 그 작업에 정한 모델 · 강도로 AI 를 띄웁니다.

```bash
devtrack watch --claude      # Claude: claude -p --model … --effort … 로 실행
devtrack watch --codex       # Codex: codex exec -m … 로 실행 (11단계)
```

- 같은 작업에 온 다음 메시지 · 승인 결정은 **같은 대화로 이어 갑니다** (Claude · Codex 모두). 그래서 작업의 맥락이 끝까지 유지됩니다.
  대화 기록이 지워져 이어 가지 못하면 새 대화로 실행하고, 새 대화는 DevTrack 기록을 읽어 이어 갑니다.
- 실행기의 Claude 는 대화창이 없어 권한을 물을 수 없으므로 `auto` 권한 모드로 실행됩니다. 바꾸려면 `--` 뒤에 적습니다
  (`devtrack watch --claude -- --permission-mode <모드>`).
- 이 터미널 창은 열어 두세요 (멈추기: Ctrl+C). 실행기와 대기 모드 대화를 함께 켜 두면 같은 지시를 둘 다 받을 수 있으니 하나만 켜 두세요.

**대기 모드 대화로 받기 (방법 B · C).** 켜 둔 대화는 자기 모델을 바꿀 수 없으므로, 모델 · 강도가 다른 작업은 받지 않고 건너뜁니다.
DevTrack 이 그 대화의 모델 · 강도를 Claude Code 기록에서 읽어 확인합니다.

- 작업 화면에 **"Claude가 기다리고 있지만, 지정한 모델과 달라 이 작업을 받지 않습니다"** 가 보이면 셋 중 하나를 합니다.
  실행기를 켜거나, 그 대화에서 `/model claude-opus-5-5` · `/effort xhigh` 로 바꾼 뒤 "T-0012 진행해줘" 라고 하거나, 작업의 모델 지정을 바꿉니다.
- 이미 진행 중인 작업의 지정을 바꾸면 다음 메시지부터 적용됩니다.

### 6-2. AI 끼리 리뷰 반복 (선택)

코드 작업은 개발이 끝나면 다른 AI 에게 리뷰를 받도록 정해 둘 수 있습니다. 예를 들어 Claude 가 개발하고 Codex 가 리뷰합니다.
리뷰에서 수정이 필요하다고 하면 개발한 AI 가 고친 뒤 다시 리뷰받고, 통과하면 커밋 승인을 요청합니다. 그 사이에 사람이 결과를 옮겨 줄 필요가 없습니다.

1. **새 작업 지시** 에서 작업 유형을 **코드 개발** 로 두고, **리뷰 받기** 에서 리뷰어 AI 와 **리뷰 최대 횟수**(기본 3번)를 고릅니다.
   리뷰어의 모델 · 추론 강도도 정할 수 있습니다 ([6-1](#/guide/s6-1)).
2. 개발이 끝나면 담당 AI 가 리뷰를 요청합니다. DevTrack 이 지금 바뀐 코드의 diff 로 **리뷰 작업**(예: `T-0012`)을 만들어 리뷰어에게 맡깁니다.
3. 리뷰어는 검토 항목(R1, R2…)과 판정(**통과** / **수정 필요**)을 남깁니다. 결과는 개발한 AI 에게 **[AI 메시지]** 로 갑니다.
4. 수정이 필요하면 개발한 AI 가 고친 뒤 다시 요청합니다. 두 번째부터는 **지난 리뷰 이후 바뀐 부분**의 diff 도 함께 갑니다.
   리뷰어는 같은 대화로 이어 가므로 앞에서 지적한 것이 고쳐졌는지 확인합니다.
5. 통과하면 개발한 AI 가 커밋 승인을 요청하고, 승인 요청에 "Codex 의 2차 리뷰를 통과한 코드입니다" 가 표시됩니다.
   **커밋 · 푸시는 지금처럼 승인해야만 진행됩니다.** 정한 횟수를 다 써도 통과하지 못하면, 남은 지적과 함께 결정을 요청합니다 (이대로 커밋 · 더 고치기 · 리뷰 더 받기).

작업 화면의 **AI 리뷰** 칸에서 차례마다 결과(예: 1차 수정 필요 → 2차 통과), 열린 항목, 리뷰한 변경을 볼 수 있습니다. 작업을 취소하면 반복도 멈춥니다.

- **두 AI 가 모두 켜져 있어야 저절로 이어집니다.** 예를 들어 한 터미널에 `devtrack watch --claude`, 다른 터미널에 `devtrack watch --codex` 를 켭니다.
  Claude 쪽은 대기 모드 대화여도 됩니다.
- **같은 AI 끼리도 됩니다** (예: Claude 가 개발하고 Claude 가 리뷰, 같은 모델이어도 됨). 이때도 리뷰는 **개발한 대화와 다른 새 대화**가 해서,
  자기가 짠 코드를 같은 맥락에서 다시 보지 않습니다. `devtrack watch --claude` 하나만 켜 두면 개발과 리뷰를 작업마다 다른 대화로 실행해 줍니다.
  개발한 대기 모드 대화는 그 리뷰 작업을 받지 않습니다 (`[다른 대화가 리뷰]`).
- **지켜지는 규칙**
  - 리뷰받기로 한 작업은 리뷰를 통과하기 전에는 커밋 승인을 요청할 수 없습니다. 통과한 뒤 코드가 바뀌면 바뀐 부분을 다시 리뷰받아야 합니다.
    리뷰 없이 커밋하려면 채팅에서 그렇게 말해 주세요.
  - 개발한 대화는 그 작업의 리뷰를 맡을 수 없습니다. 같은 대화에서 리뷰하게 하려면 채팅에서 그렇게 말해 주세요.
  - 리뷰어는 파일을 고치지 않고 리뷰만 합니다. 커밋이 반영되면 그 작업의 다음 변경은 다시 리뷰받고, 횟수도 새로 셉니다.
- **diff 에는 바뀐 코드만 들어갑니다.** CMake 빌드 폴더(`CMakeCache.txt` 가 있는 폴더), `CMakeFiles/`, 오브젝트 · 라이브러리 · 실행 파일(`.o` · `.a` · `.so` 등), `build/` · `cmake-build-*/` 같은 빌드 폴더, `__pycache__/` 는 `.gitignore` 에 없어도 리뷰 diff 와 커밋에서 빠지고, 무엇을 뺐는지 따로 표시됩니다.
  빠진 파일을 꼭 넣어야 하면 파일 이름을 그대로 적어 요청합니다 (`--files`).
- **AI 끼리 직접 묻고 답하기:** `devtrack send <작업> "메시지"` 는 그 작업을 맡은 AI 의 받은 편지함에 [AI 메시지] 로 갑니다.
  사용자 지시가 아니므로, 승인이 필요한 일은 여전히 사용자에게 묻습니다.
- 터미널에서는 `devtrack new … --review-by Codex --review-rounds 3` 으로 정하고, 이미 만든 작업은 `devtrack review-request T-0001 --reviewer Codex` 로 요청합니다.

### 6-3. 논문 심사 반복 (선택)

논문 작업은 원고를 다 쓰면 다른 AI 가 **투고할 저널의 심사위원 관점**으로 심사하고, 저자 AI 가 심사대로 고친 뒤 다시 심사받게 할 수 있습니다.
실제 저널 심사처럼 판정(**게재 가능 · 소폭 수정 · 대폭 수정 · 게재 불가**), 심사 항목(R1, R2…), 저자의 **답변서**(response to reviewers)가 오갑니다.

1. **새 작업 지시** 에서 작업 유형을 **논문 작성** 으로 두고 **심사 받기** 에서 심사위원 AI 와 최대 횟수를 고릅니다.
   **심사할 원고**(예: `paper/main.tex`, Word `.docx`, PDF, Markdown)와 **투고처**(예: Journal of Fluid Mechanics)를 적습니다.
   원고를 비워 두면 AI 가 심사를 요청할 때 정합니다. 심사위원의 모델 · 추론 강도도 정할 수 있습니다 ([6-1](#/guide/s6-1)).
2. 원고를 다 쓰면 저자 AI 가 심사를 요청합니다. **심사 작업**(문서 리뷰)이 만들어지고, 그때의 원고가 붙습니다.
   - LaTeX 는 본문과 `\input` · `\include` 로 불러오는 파일, 참고문헌(`.bib`), 같은 이름의 PDF 까지 함께 붙습니다.
     원고가 `\includegraphics` 로 부르는 **그림**도 붙어서 심사위원이 그림을 직접 봅니다. 그림만 고친 차례도 다시 심사받을 수 있고,
     바뀐 그림은 심사 요청에 이름이 적힙니다.
   - Word 는 원본과 글자를 함께 붙입니다.
3. 심사위원 AI 는 새로움 · 선행 연구 대비 기여, 방법의 타당성, 결과가 결론을 뒷받침하는지, 그림 · 표, 문장을 봅니다.
   항목마다 위치 · 원문 · 고칠 방법(원고의 언어로)을 남기고, 심사평(referee report)과 판정을 보냅니다.
4. 수정이 필요하면 저자 AI 가 원고를 고치고 **답변서**를 써서 다시 요청합니다. 2차부터는 답변서가 꼭 필요합니다.
   - 답변서는 항목마다 `R1`, `R2` … 로 나뉩니다. 질문에는 답을, 요청에는 어떻게 고쳤는지(고치지 않았다면 그 이유)를 적습니다.
   - 지난 차례의 열린 항목 중 답이 없는 것이 있으면 요청이 거절됩니다.
   - 심사위원은 **지난 심사 이후 바뀐 부분** 과 답변서를 보고, 같은 대화로 이어 가며 앞의 지적이 해결됐는지 확인합니다.
5. **게재 가능** 이 나오면 저자 AI 가 결과를 알려 드립니다. 게재 불가가 나오거나 정한 횟수를 다 쓰면 다음에 어떻게 할지 결정을 요청합니다.
   어느 쪽이든 아래의 **심사 · 답변 기록**을 첨부합니다.

**심사 · 답변 기록** — 심사위원이 남긴 질문 · 요청과 저자의 답을 차례별로 모은 리포트입니다. 논문 작업의 결과물로 올라갑니다.
- 맨 위 표에 차례마다 판정, 질문 · 요청 수, 답한 수, 다음 심사에서 해결된 수가 나옵니다.
- 이어서 항목마다 위치 · 원고 원문 · 심사위원의 질문이나 요청, 저자 답변, 다음 차례의 해결 여부가 나옵니다.
- 심사 판정과 답변서가 올 때마다 DevTrack 이 새 버전으로 고칩니다. 지난 버전도 남습니다.

작업 화면의 **AI 심사** 칸에서 차례마다 판정, 열린 항목, 원고 · 바뀐 부분 · 답변서와 **심사 · 답변 기록** 링크를 볼 수 있습니다. 심사 작업은 **문서 리뷰** 화면에도 나옵니다.

- 코드 리뷰와 같은 규칙이 적용됩니다. 두 AI 가 모두 켜져 있어야 저절로 이어지고, 원고를 쓴 대화는 그 심사를 맡지 않으며, 심사위원은 원고를 고치지 않습니다.
- 논문 심사는 커밋을 막지 않습니다 (원고 초안을 저장소에 자주 올려도 됩니다).
- 터미널에서는 `devtrack new … -t paper --review-by Codex --review-doc paper/main.tex --review-venue "J. Fluid Mech."`, 다시 요청할 때는
  `devtrack review-request T-0005 --response response.md` 입니다.

## 7. 진행 상황 보기

- **대시보드** — 진행 중 · 승인 대기 · 열린 문제 · 완료 수, 확인이 필요한 항목, 진행 중인 작업 카드, 최근 활동.
- **작업** — 전체 작업 목록. 작업을 누르면 상세 화면으로 갑니다.
- **작업 상세** — 제목 아래에 담당 AI · 모델 · 저장소 · 관련 작업, 그 아래 "지금 하는 일"과 진행률, 아래 탭으로 나뉩니다.
  - 개요: 지시 내용, 작업 계획 체크리스트, 최근 기록, 열린 문제, 결과물. 리뷰 · 심사를 정한 작업은 맨 위에 **AI 리뷰** · **AI 심사** 칸이 있습니다 ([6-2](#/guide/s6-2), [6-3](#/guide/s6-3))
  - 진행 기록 · 문제점 · 결과물 · 승인 (논문이면 빌드 탭도 생깁니다)
- **활동 기록** — 모든 작업의 기록을 날짜별로 모아 봅니다 (최근 300건).
- **알림** — 오른쪽 위 종 아이콘에 승인 대기 수가 표시되고, 새 승인 요청 · 문제 · 완료가 생기면 화면 구석에 알림이 뜹니다.
  종 아이콘 메뉴에서 **데스크톱 알림 켜기** 를 누르면 다른 창을 보고 있어도 알려 줍니다.
- 화면은 **10초마다 자동으로** 새로 고쳐집니다. 로컬 서버든 정적 웹이든 AI 가 남긴 기록 · 결과물이 브라우저 새로고침 없이 나타나고,
  다른 탭에 있다가 돌아오면 바로 확인합니다. 바로 보고 싶으면 오른쪽 위 새로고침 버튼을 누르세요.
  (정적 웹은 AI 의 기록이 웹 공개 폴더로 옮겨져야 바뀝니다 — [10단계](#/guide/s10))
  - 입력 칸에 써 두기만 한 글은 화면이 새로 고쳐져도 그대로 남습니다.
  - 입력 칸에 커서가 있는 동안(글을 쓰는 중) · 승인 선택지를 고른 동안에는 화면을 바꾸지 않고 **새 업데이트 보기** 를 띄웠다가, 입력 칸에서 나오면 저절로 반영합니다.
    **새 작업 지시** 화면은 쓰기 시작하면 쓰던 내용이 지워지지 않도록 다시 그리지 않습니다.
  - 결과물이 새 버전으로 바뀌면 그림 · PDF 도 새 파일로 다시 불러옵니다.
- **결과물 보기 방식** — **결과물** 화면과 작업의 **결과물** 탭 오른쪽 위의 단추로 **카드**(격자)와 **목록**(세로로 한 줄씩)을 바꿉니다.
  목록은 제목을 줄이지 않고 작업 번호 · 종류 · 시간 · 크기를 함께 보여 주며, 그림은 작은 미리보기가 붙습니다. 고른 방식은 브라우저에 기억됩니다.
- **결과물 순서** — 그 옆의 **최신순** · **작업별** 단추로 바꿉니다. 처음에는 **최신순**으로, 마지막으로 올리거나 새 버전이 된 결과물이 맨 위에 옵니다.
  **작업별**은 작업 번호가 큰 작업부터 작업마다 제목 줄을 달아 묶고, 작업 안에서는 만든 순서(F-1, F-2 …)로 보여 줍니다.
  작업의 **결과물** 탭에서는 **최신순** · **만든 순서** 로 나옵니다. 고른 순서도 브라우저에 기억됩니다.
- **화면 언어 (English / 한국어)** — 처음 열면 영어 화면입니다. 오른쪽 위 **한** 단추를 누르면 메뉴 · 머리말 · 버튼 · 상태 라벨 같은
  화면 틀과 이 사용 방법 문서가 한국어로 바뀌고, **EN** 을 누르면 영어로 돌아옵니다. 고른 언어는 브라우저에 기억됩니다. 작업 제목 · 지시 · 진행 기록 · 결과물 · 리뷰 리포트는 쓰인 언어(한국어) 그대로입니다.
  AI 에게 보내는 메시지(정적 모드의 붙여 넣기 문구)도 한국어로 만들어집니다.

## 8. 승인 · 수정 요청 · 거절

Claude 가 확인이 필요한 지점에 오면 **승인 요청** 메뉴와 종 아이콘에 표시됩니다.

1. 요청을 열면 설명과 함께 검토할 내용(코드 변경 diff, 리포트, 그림 등)이 펼쳐집니다.
2. 필요하면 코멘트를 적고 버튼을 누릅니다.

   | 버튼 | 결과 |
   |---|---|
   | **승인** | Claude 가 다음 단계로 진행합니다. 커밋 요청이면 그 내용 그대로 커밋 · 푸시합니다 |
   | **수정 요청** | 코멘트(필수)대로 고친 뒤 새 승인 요청을 올립니다 |
   | **거절** | 그 내용은 진행하지 않습니다 |

3. 목록에서 고르는 요청(예: "코멘트를 작성할 항목을 골라주세요")은 체크한 항목만 진행됩니다.

안전장치: 커밋 요청은 **승인한 diff 와 실제 변경이 조금이라도 다르면 실행되지 않습니다.** 승인 이후 코드가 바뀌면 Claude 가 새 요청을 올립니다.
커밋에는 diff 에 넣은 파일만 들어갑니다. 빌드 결과물(CMake 빌드 폴더, `.o` · 실행 파일 등)은 `.gitignore` 에 없어도 빠지고, 승인 요청에 **뺀 빌드 결과물** 로 표시됩니다 ([6-2](#/guide/s6-2)).

작업 중에 하고 싶은 말이 있으면 작업 상세 화면 **진행 기록** 탭의 **Claude에게 메시지** 칸(담당 AI 이름)에 적어 보내세요. Claude 가 다음 단계에서 확인합니다.
진행 기록의 사용자 메시지에는 AI 가 확인했는지(**AI 확인함** / **AI 확인 전**)가 표시됩니다.

**결과물 수정 요청 · 추가 지시** — 결과물(리포트 · 그림 · 표 · 코드 등)을 열면 맨 아래에 이 칸이 있습니다.
- 여기서 보낸 메시지는 **그 결과물에 대한 메시지**로 AI 에게 갑니다 (예: "2열을 백분율로 바꿔 주세요", "같은 방식으로 3D 그림도 만들어 주세요").
- AI 는 고친 결과물을 같은 결과물의 **새 버전(v2, v3…)** 으로 올립니다. 같은 화면에서 새 버전을 보고, 이전 버전은 "이전 버전" 링크로 봅니다.
- 한 번 보내면 칸 위에 **이 결과물에 보낸 요청과 새 버전**이 차례로 쌓입니다 (요청 → v2 → 다음 요청 …).
- 정적 모드에서는 Claude 에게 붙여 넣을 메시지를 만들어 줍니다. 터미널에서는 `devtrack comment T-0003 --artifact F-2 "…"`.

### 완료로 처리 · 작업 취소 · 삭제

작업 상세 화면 오른쪽 위의 버튼을 씁니다.

| 버튼 | 결과 | 되돌리기 |
|---|---|---|
| **완료로 처리** | 끝나지 않았더라도 상태가 '완료'(진행률 100%)로 바뀝니다. 남은 부분을 직접 마무리했거나 더 진행할 필요가 없을 때 씁니다. 기록 · 결과물은 남고, 결정을 기다리던 승인 요청은 철회됩니다 (커밋 요청이었다면 커밋되지 않음). 메모를 남길 수 있습니다 | 기록이 남아 있음 |
| **작업 취소** | 상태가 '취소'로 바뀌고 진행 중 목록에서 빠집니다. 기록 · 결과물은 남고, 결정을 기다리던 승인 요청은 철회됩니다 | 기록이 남아 있음 |
| **삭제** | 기록, 결과물 파일, 승인 요청까지 **모두 지웁니다.** 다른 작업과의 연결도 풀립니다 | 불가능 |

- 삭제 버튼을 누르면 **확인 창**이 뜨고, 작업 ID(예: `T-0003`)를 그대로 입력해야 **영구 삭제** 버튼이 눌립니다.
- 어느 것이든 담당 AI 에게 "이 작업을 멈추라"는 알림이 갑니다. 언제 멈추는지는 AI 가 일하는 방식에 따라 다릅니다.
  - `devtrack watch` 로 실행 중인 작업: **바로** 멈춥니다 (실행 중인 AI 를 종료).
  - 대화 중인 Claude · Codex: 훅(5-4, 11단계 ⑤)을 설치했으면 **다음 명령 · 파일 수정 직전에** 멈춥니다.
    훅이 없으면 지금 단계가 끝나고 inbox 를 확인할 때 멈춥니다.
  - AI 가 명령 없이 긴 답을 쓰는 동안에는 끼어들 수 없습니다. 급하면 대화 창의 중지 버튼을 누르세요.
- 보통은 **취소**를 쓰고, 잘못 만든 작업이나 테스트 작업만 **삭제**하세요. 지운 작업 번호는 다시 쓰이지 않습니다.
- 정적 모드에서는 세 버튼 모두 Claude 에게 보낼 메시지를 만들어 줍니다.
- 터미널에서는 `devtrack done T-0003 --by-user -m "메모"`, `devtrack cancel T-0003 -m "사유"`, `devtrack delete T-0003` (작업 ID 를 다시 입력해 확인).

## 9. 분야별 사용법

### 코드 개발

1. 유형 **코드 개발**, 대상 저장소 경로를 적어 지시합니다.
2. **코드 개발** 메뉴에서 코드 작업을 모아 봅니다.
   - 작업 카드마다 대상 저장소 · 브랜치와 지금 하는 일
   - **반영된 커밋**: 승인 후 실제로 커밋 · 푸시된 기록 (커밋 해시를 누르면 GitHub 에서 열림)
   - **코드 · 변경사항**: AI 가 올린 코드 파일과 diff
   - **승인 대기** 필터는 확인이 필요한 작업만 보여 줍니다
3. 결과는 **승인 요청** 에서 diff 로 확인합니다. 승인하면 Claude 가 커밋하고 푸시합니다 (커밋 해시가 기록됩니다).

### 코드 리뷰

1. Claude 채팅에 `/review-pr https://github.com/<조직>/<저장소>/pull/<번호>` — 또는 웹에서 유형 **코드 리뷰** 로 지시하고 지시 내용에 같은 명령을 적습니다.
2. **코드 리뷰** 메뉴에 리뷰가 올라옵니다.
   - **리뷰 결과 한눈에 보기**: 한 줄 결론, 리뷰 의견, 중요도별 남은 항목(반드시 수정 · 수정 권장 · 개선 제안 · 사소함 · 질문)
   - 항목마다 **쉬운 설명**과 GitHub 코드 위치 링크
   - 아래에 전체 리포트 — 한국어로, 개발자가 아니어도 읽을 수 있게 작성됩니다. 같은 내용의 **PDF** 도 함께 첨부되어 내려받거나 공유할 수 있습니다.
     리포트가 고쳐지면 같은 결과물이 **새 버전(v2, v3…)** 으로 바뀌고, 이전 버전은 결과물 화면의 "이전 버전" 링크로 볼 수 있습니다
3. **PR 코멘트를 작성할 항목**을 체크하고 **선택한 항목으로 진행** 을 누릅니다. 아직 PR 에는 아무것도 올라가지 않습니다.
4. Claude 가 고른 항목의 코멘트 초안을 올리면, 확인하고 **승인** 해야 PR 에 게시됩니다.

### 논문 작성

1. 유형 **논문 작성** 으로 지시합니다. 장 · 절 구성을 지시에 적으면 작업 계획 체크리스트로 표시됩니다.
2. **논문 작성** 메뉴에서 논문별로 확인합니다.
   - **컴파일된 PDF** (쪽수, 정의 안 된 인용 · 참조 경고, 컴파일 실패 시 오류 위치)
   - `.tex` 원고는 코드 대신 **문서 보기** 로 읽을 수 있습니다 (수식 · 표 · 그림 포함, 원본 코드로 전환 가능)
   - 그림, 연결된 데이터 분석, 열린 문제
3. 논문에 쓸 분석이 필요하면 논문 카드의 **이 논문용 분석 지시** 를 누르세요. 분석 작업이 논문과 연결됩니다.
4. **원고 폴더** — 논문 작업마다 기록 폴더의 `tasks/<작업 번호>/paper/` 에 그대로 컴파일하거나 Overleaf 에 올릴 수 있는 원고가 모입니다.
   - AI 가 올린 최신 `.tex` · `.bib` 가 원래 파일 이름으로 들어가고, 원고가 `\includegraphics` 로 부르는 그림은 같은 이름의
     그림 결과물(이 작업, 없으면 연결된 분석 작업)에서 `figures/` 에 모입니다. 원고가 부르지 않는 그림은 넣지 않습니다.
   - 원고는 `\graphicspath{{figures/}}` 를 쓰고 그림을 확장자 없이(`\includegraphics{fig_kappa}`) 부르게 해 두면,
     PDF 그림이 없을 때 PNG 로도 컴파일됩니다. AI 의 작업 규칙에 들어 있습니다.
   - 결과물이 바뀔 때마다 저절로 다시 만들어지므로 이 폴더의 파일은 직접 고치지 마세요.
     `devtrack paper <작업 번호>` 로 지금 상태와 빠진 그림(확장자가 안 맞는 그림 · 결과물이 없는 그림)을 확인합니다.
   - 기록 폴더만 다른 컴퓨터로 옮겨도 원고가 함께 따라갑니다. 예를 들어 Mac 에서 쓰던 논문을 HPC 에서 이어 쓸 수 있습니다.

### 문서 리뷰

논문 · 보고서 · 제안서를 Claude 에게 읽혀 **요약**과 **보완 · 수정할 부분**을 받습니다. 결과는 PDF 리포트로 올라옵니다.

1. 유형 **문서 리뷰** 로 지시합니다. 웹의 새 작업 지시 화면에서 유형을 고르면 칸이 바뀝니다.
   - **검토할 문서 경로**: PDF · Word(`.docx`) · LaTeX(`.tex`) 파일 — Claude 가 일하는 컴퓨터의 경로 (옛 `.doc` 는 `.docx` 나 PDF 로 저장해 주세요)
   - **문서 종류**: 과학 논문 · 보고서 · 제안서 · 학위 논문 · 기타
   - **문서의 목적 · 제출처**: 예) 학술지 투고 전 점검, 과제 제안서 심사 대비 — 이 목적에 맞게 잘 썼는지를 기준으로 봅니다
   - 채팅에서는 `/review-doc ~/papers/draft.pdf 학술지 투고 전 점검` 처럼 지시해도 됩니다 (스킬 설치: [5-2단계](#/guide/s5-2))
2. Claude 는 이 순서로 봅니다: 문서 요약 → 목적에 비해 빠진 부분 → 전반적인 논리 → 어색한 문장 · 맞춤법.
   **과학 논문**은 형식, 선행 연구와 무엇이 다른지, 결론을 이끄는 논리를 더 자세히 봅니다.
3. **문서 리뷰** 메뉴에서 결과를 봅니다.
   - **리뷰 결과 한눈에 보기**: 리뷰 의견(제출 가능 · 소폭 수정 · 대폭 보완 · 다시 작성)과 한 줄 결론, **문서 요약**,
     영역별 평가(양호 · 보완 필요 · 미흡), 잘된 점
   - **보완 · 수정할 부분**: 항목(R1, R2…)마다 쉬운 설명과 위치(쪽 · 절), 해당하면 **원문 → 수정 제안**.
     맞춤법 같은 사소한 항목은 접혀 있습니다
   - 아래에서 **리뷰 리포트(PDF)** 와 **원본 문서**를 바꿔 봅니다. Word 원본은 글자 · 표만 뽑아 보여 줍니다 (그림 · 서식은 다운로드해서 확인)
4. Claude 가 "리포트를 확인해 주세요" 를 올리면 확인하고 **승인** 합니다. 고쳐 달라는 부분은 코멘트나 **리뷰에 대한 의견 보내기** 로 적습니다.
   원문을 직접 고친 수정본이 필요하면 "R1, R3 반영한 수정본 만들어 줘" 라고 보내세요 — 원본 파일은 그대로 두고 수정본을 따로 올립니다.

### 데이터 분석 · 시각화

1. 유형 **데이터 분석** 또는 **시각화** 로 지시합니다. 데이터 위치와 무엇을 알고 싶은지 적어 주세요.
2. **데이터 분석** 메뉴에서 그림 갤러리, 표(CSV), 노트북, 요약 리포트를 봅니다. **논문용** 필터는 논문에 연결된 분석만 보여 줍니다.
3. 해석이 필요한 결과는 Claude 가 승인 요청(결과 확인)으로 올립니다.

### 브레인스토밍

1. 유형 **브레인스토밍** 으로 지시합니다. 주제와 조건(기간 · 쓸 수 있는 데이터와 계산 자원 · 범위), 아이디어마다 알고 싶은 것
   (필요한 것 · 위험 · 기대 효과 등)을 적어 주세요. 채팅에서 "○○ 브레인스토밍 해줘" 라고 해도 됩니다.
2. **브레인스토밍** 메뉴에서 봅니다.
   - 왼쪽 목록에서 고르면 주제 · 진행 계획과 Claude 가 정리한 **아이디어 노트**가 보입니다. 노트가 여러 개면 노트 위쪽 단추로 바꿔 봅니다.
   - Claude 가 "더 구체화할 아이디어를 골라주세요" 같은 요청을 올리면 이 화면에서 바로 체크하고 **선택한 항목으로 진행** 을 누릅니다.
     고른 아이디어는 **고른 아이디어** 에 쌓이고, Claude 는 고른 것만 더 구체화합니다.
   - 떠오른 생각이나 바뀐 조건은 아래 **아이디어 · 의견 보내기** 칸으로 보냅니다.
3. 해 볼 아이디어가 정해지면 **이 아이디어로 작업 지시** 를 누르세요. 새 작업(코드 개발 · 데이터 분석 · 논문 작성 등)이
   이 브레인스토밍과 연결되어 **연결된 작업** 에 표시됩니다.

## 10. HPC 에서 쓰기

슈퍼컴퓨터(HPC) 같은 원격 서버에서는 Claude 가 그 서버에서 일하고, 기록도 그 서버에 남습니다. 그 기록을 웹으로 보는 방법은 두 가지입니다.
아래의 모듈 이름 · 경로 · 접속 주소는 예시이니, 쓰는 시스템에 맞게 바꾸세요.

| | 정적 웹 ([10-6](#/guide/s10-6)) | 실시간 · SSH 터널 ([10-5](#/guide/s10-5)) |
|---|---|---|
| 보는 곳 | HPC 의 웹 공개 폴더(예: `~/www`) 주소 | 내 컴퓨터 브라우저의 `localhost` (터널 경유) |
| 승인 · 지시 | 웹이 만든 메시지를 HPC 의 Claude 대화에 붙여 넣기 | 웹에서 바로 저장 — 기다리던 Claude 가 바로 시작 |
| 켜 두는 시간 | 항상 (기록할 때마다 자동 반영) | 웹을 쓰는 동안만 |
| 주의 | 주소를 아는 누구나 볼 수 있음 — 비밀번호를 걸 수 있음 ([10-7](#/guide/s10-7)) | 켜 있는 동안 같은 로그인 노드의 다른 사용자도 접속할 수 있음 (같은 비밀번호로 막힘) |

평소에는 정적 웹으로 진행 상황을 보고, 지시하거나 승인할 때만 실시간 방식을 잠깐 켜는 것을 권합니다.
처음이라면 10-1 → 10-3 → 10-4 → 10-5 순서로 따라 하세요 (10-2 는 내 컴퓨터의 기록을 옮길 때만).

### 10-1. DevTrack 설치 (처음 한 번)

```bash
module load python               # 3.7 이상 파이썬 (모듈 이름은 시스템마다 다름)
git clone git@github.com:hyungyukang/DevTrack.git ~/devtrack
cat >> ~/.bashrc <<'EOF'
module load python
export PATH="$HOME/devtrack/bin:$PATH"
EOF
source ~/.bashrc
devtrack --version
devtrack config data $HOME/devtrack-data
devtrack config publish $HOME/www/devtrack     # 웹 공개 위치 (환경에 맞게)
devtrack publish               # 처음 한 번 (웹 화면을 업데이트했을 때도)
```

- `module load python`: 시스템 기본 `python3` 가 3.7 미만일 때 필요합니다. 모듈 이름은 시스템마다 다르니 `module avail python` 으로 확인하세요
  (기본 `python3` 가 3.7 이상이면 두 줄 모두 빼도 됩니다). `~/.bashrc` 에도 넣어 두는 것이 중요합니다.
  Claude 와 취소 훅(5-4)도 이 파이썬을 써야 합니다 ([10-3](#/guide/s10-3)).
- `git clone` 을 하려면 HPC 에 GitHub SSH 키가 등록되어 있어야 합니다.
- 이후 Claude 가 기록할 때마다 공개 디렉토리에 자동으로 반영됩니다.
  센터가 웹 공개 폴더를 제공하지 않으면 `devtrack config publish` 와 `devtrack publish` 는 빼고 실시간 방식([10-5](#/guide/s10-5))으로 보세요.
- **DevTrack 을 업데이트(`git pull`)한 뒤에는 `devtrack publish` 를 다시 실행하세요.** 기록은 저절로 반영되지만 웹 화면 파일은 이 명령으로만 복사됩니다.
  공개할 때 화면 파일 주소에 버전을 붙이므로, 웹 서버가 캐시 설정을 막아 두어도 브라우저에서 새로고침 한 번이면 새 화면이 보입니다.
- 기록 · 공개 폴더는 설정 파일(`~/.config/devtrack/config.json`)에 저장됩니다. 그래서 셸 설정을 읽지 않고 켜진 프로그램도 같은 곳을 씁니다.
  VS Code 의 Claude 와 훅, tmux, 먼저 켜 둔 `serve` 가 그런 예입니다. `devtrack config` 로 확인하세요.
  전에 `~/.bashrc` 에 `export DEVTRACK_DATA` · `DEVTRACK_PUBLISH_DIR` 를 넣었다면 그 줄은 지우세요.
  환경 변수가 있으면 그쪽이 먼저 쓰여서, 값이 다르면 기록이 두 곳으로 나뉩니다.
- **기록 폴더는 홈에 두세요.** 스크래치(scratch) 같은 병렬 파일 시스템의 작업 공간은 한동안 읽거나 고치지 않은 파일을 지우는(purge) 경우가 많아 오래된 작업 기록이 사라질 수 있습니다.
  프로젝트 공유 공간은 같은 프로젝트 구성원도 들어올 수 있습니다.
  홈은 보통 지워지지 않고 백업됩니다. 자세한 정책은 쓰는 센터의 안내를 확인하세요.

### 10-2. 내 컴퓨터에서 쓰던 기록 옮기기 (선택)

로컬(Mac 등)에서 쓰던 작업 기록을 HPC 에서 이어서 쓰려면 아래 순서로 옮깁니다. 기록 폴더 하나가 전부라 옮기기는 간단합니다.

**① 옮기기 전 (내 컴퓨터에서)**
- **승인 대기 정리:** 결정을 기다리는 승인 요청은 가능하면 미리 처리하세요. 특히 **커밋 승인 요청**은 내 컴퓨터의 저장소 경로로 되어 있어 HPC 에서는 반영할 수 없습니다.
- **내 컴퓨터에만 있는 파일:** 그런 파일에 기대는 작업은 끝내고 옮기거나, 그 파일도 함께 옮기세요. 예: 코드 리뷰 코멘트 초안(`~/.pr-review/`), 로컬 폴더의 논문 원고, 데이터.
- **로컬은 끄기:** `devtrack serve` 와 대기 모드("웹 지시 기다려줘")를 끄세요. **두 곳에서 동시에 기록하면 내용이 갈라집니다.** 옮긴 뒤에는 HPC 쪽만 씁니다.

**② 기록 복사 (내 컴퓨터에서)** — 10-1 설치를 마친 뒤 실행합니다.

```bash
rsync -av --exclude '.agent/' --exclude '.lock' \
  ~/devtrack/data/ <사용자 ID>@<HPC 로그인 주소>:~/devtrack-data/
```

- 내 컴퓨터의 기록 폴더(`devtrack config` 로 확인, 기본 `~/devtrack/data/`)를 HPC 의 기록 폴더로 복사합니다.
- `.agent/` 는 그 컴퓨터의 대화 · 대기 상태라 옮기지 않습니다. `.lock` 은 잠금 파일입니다.
- 처리 여부(확인한 지시 · 결정)는 각 작업 파일에 들어 있어서, 이미 처리한 지시가 HPC 에서 다시 뜨지 않습니다.
  지운 작업 번호 목록(`.deleted.json`)도 함께 옮겨지므로 번호가 다시 쓰이지 않습니다.
- 결과물 파일은 기록 폴더 안에 복사되어 있으므로 그대로 보입니다(`--no-copy` 로 경로만 기록한 결과물은 제외).
  논문 작업의 원고 폴더(`tasks/<작업 번호>/paper/`, [9. 논문 작성](#/guide/s9))도 기록 폴더 안이라 함께 옮겨집니다.
  끝난 작업에 적힌 로컬 저장소 경로는 그대로 남지만 보기에는 문제없습니다.
- 코드 리뷰를 이어서 하려면 `~/.pr-review/` 폴더도 같은 방법으로 HPC 의 홈으로 복사하세요.

**③ 웹 갱신 (HPC 에서)** — `devtrack publish` 를 한 번 실행합니다.

**④ Claude 설정** — [10-3](#/guide/s10-3).

**⑤ 확인 (HPC 에서)**
- `devtrack list` 에 옮긴 작업이 보이는지, `devtrack inbox` 가 오류 없이 실행되는지 봅니다.
- 웹 주소를 열어 작업과 결과물이 보이는지 봅니다.

### 10-3. Claude Code 설치 · 설정 (처음 한 번)

**① 설치** — HPC 에서 실행합니다. 홈의 `~/.local/bin/claude` 에 설치되며 관리자 권한은 필요 없습니다.

```bash
curl -fsSL https://claude.ai/install.sh | bash      # 내려받는 동안 진행 표시가 없습니다
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc
source ~/.bashrc
claude --version                                     # 버전 번호가 나오면 성공
```

- `claude: command not found` 가 나오면 `ls ~/.local/bin/claude` 로 설치됐는지 보고, 있으면 위의 PATH 줄을 확인하세요.

**② 로그인** — `claude` 를 처음 실행하면 로그인 안내가 나옵니다. HPC 에는 보통 브라우저가 없으므로, 화면에 나온 주소를 **내 컴퓨터 브라우저**에서 열어 로그인하고, 나온 코드를 HPC 터미널에 붙여 넣습니다.

**③ 자동 업데이트 끄기 (권장)** — HPC 의 홈은 보통 모든 로그인 노드가 함께 쓰는 네트워크 디스크입니다.
한 노드에서 Claude Code 가 자동 업데이트하며 예전 버전 파일을 지우면, 다른 노드의 tmux(10-4)에서 돌던 Claude 가 `Bus error` 로 꺼질 수 있습니다.
`~/.claude/settings.json` 에 아래를 넣고(파일이 이미 있으면 `env` 안에 한 줄만 추가), 업데이트는 Claude 가 하나도 돌지 않을 때 `claude update` 로 직접 하세요.

```json
{
  "env": { "DISABLE_AUTOUPDATER": "1" }
}
```

**④ DevTrack 설정** — 5단계를 HPC 에서 똑같이 하되, 아래를 지켜 주세요.

- **기록 규칙(5-1):** `~/.claude/CLAUDE.md` 의 경로를 HPC 의 위치(`~/devtrack/...`)로 적습니다. 내 컴퓨터의 파일을 복사했다면 경로가 내 컴퓨터 기준이니 꼭 바꾸세요.
- **코드 리뷰 스킬(5-2):** HPC 의 `~/devtrack` 을 가리키도록 링크를 다시 겁니다. 코드 리뷰에는 `gh auth login` 도 필요합니다.
  리포트 메일 기능은 HPC 에서 메일 설정을 한 번 새로 하세요. 비밀번호가 든 설정 파일은 복사하지 마세요.
- **취소 훅(5-4):** `"command"` 에 HPC 의 전체 경로를 적습니다. `echo $HOME/devtrack/bin/devtrack-hook` 으로 확인하세요.
- **⚠️ Claude 는 3.7 이상 파이썬이 잡힌 셸(10-1 의 `module load` 를 한 셸)에서 실행하세요.** Claude 를 띄우기 전에 `python3 --version` 이 3.7 이상인지 보세요.
  훅은 3.7 미만 파이썬으로 실행되면 Claude 를 막지 않으려고 **아무 일도 하지 않고** 넘어갑니다.
  그러면 웹에서 작업을 취소해도 Claude 가 바로 멈추지 않습니다.
- 직접 하기 번거로우면 HPC 의 Claude 에게 맡겨도 됩니다 — **"`~/devtrack/web/guide.md` 의 5-1, 5-4, 10-3 절을 읽고 이 HPC 환경에 맞게 DevTrack 설정해줘"**.
  설정을 바꾼 뒤에는 Claude 를 다시 띄워야 반영됩니다.

### 10-4. tmux 안에서 Claude 띄워 두기

tmux 는 원격 컴퓨터에 터미널 화면을 열어 두는 프로그램입니다. ssh 접속이 끊기거나 노트북을 덮어도 그 안의 Claude 는 계속 일하고, 다시 접속해 같은 화면으로 돌아갈 수 있습니다.

**① 처음 띄우기** (HPC 에서)

```bash
hostname                  # 예: login05 — tmux 를 연 로그인 노드를 기억해 두세요
tmux new -s claude        # 'claude' 라는 이름의 tmux 화면 열기
python3 --version         # 3.7 이상인지 (아니면 module load python)
cd <작업할 디렉토리>
claude
```

Claude 가 뜨면 **"웹 지시 기다려줘"** 라고 하세요. 웹에서 지시하는 방법은 [10-5](#/guide/s10-5) 입니다.

**② 빠져나오기** — `Ctrl+b` 를 눌렀다 뗀 뒤 `d`. Claude 는 뒤에서 계속 실행되므로 이제 ssh 를 끊어도 됩니다.

**③ 다시 들어가기**

```bash
ssh <사용자 ID>@<HPC 로그인 주소>
hostname                  # 처음과 다른 노드라면
ssh login05               # tmux 를 연 노드로 이동
tmux attach -t claude
```

tmux 화면은 그것을 연 로그인 노드에만 있습니다. 로그인 주소가 여러 로그인 노드를 묶은 것이면 접속할 때마다 다른 노드에 배정될 수 있으니 위처럼 옮겨 가세요.
열린 화면 목록은 `tmux ls` 로 봅니다.

| 키 (`Ctrl+b` 를 누르고 뗀 뒤) | 하는 일 |
|---|---|
| `d` | 빠져나오기 (Claude 는 계속 실행) |
| `[` | 위로 스크롤 (화살표 · PgUp, 끝낼 때 `q`) |
| `c` | 새 창 만들기 |
| `n` / `p` | 다음 / 이전 창으로 |

**④ 끝내기** — tmux 안에서 Claude 를 종료(`/exit`)하고 `exit`. 밖에서 닫으려면 `tmux kill-session -t claude`.

- `tmux` 가 없다고 나오면 `screen` 을 쓰세요 — 시작 `screen -S claude`, 빠져나오기 `Ctrl+a` 뒤 `d`, 다시 들어가기 `screen -r claude`.
- 정비 등으로 로그인 노드가 다시 시작되면 tmux 화면도 사라집니다. 그때는 ①부터 다시 하세요.
- **무거운 계산은 계산 노드에서:** Claude 는 로그인 노드에서 일합니다. 로그인 노드는 여러 사람이 함께 쓰므로, 계산이나 메모리를 많이 쓰는 작업은 할 수 없습니다(대부분 HPC 센터의 정책).
  대용량 데이터 처리 같은 일은 계산 노드에서 하도록 지시에 적어 주세요. 대화형 할당(Slurm 이면 `salloc`)이나 배치 작업을 쓰면 됩니다.
  할당 시간이 드는 일이니, 제출 전에 확인받고 싶으면 지시에 "작업 제출 전에 승인받아줘" 라고 적으세요.

### 10-5. 웹에서 바로 지시 · 승인하기 (실시간 방식, SSH 터널)

HPC 에서 `devtrack serve` 를 켜고 내 컴퓨터에서 SSH 터널로 열면, 로컬에서 쓰듯 웹에서 새 작업을 지시하고 승인을 바로 저장할 수 있습니다.
tmux 에서 기다리는 Claude(10-4)가 몇 초 안에 받아 HPC 에서 일합니다.

> **⚠️ 웹을 쓰는 동안만 켜고, 끝나면 바로 끄세요.**
> 로그인 노드는 여러 사람이 함께 쓰는 컴퓨터라, 서버가 켜져 있는 동안에는 **같은 노드의 다른 사용자도** 그 서버에 접속할 수 있습니다.
> DevTrack 서버에는 아직 로그인(인증) 기능이 없어서, 다른 사람이 기록을 보거나 승인 · 커밋 · 삭제를 누를 수 있습니다.
> 서버를 tmux 에 넣어 계속 켜 두지 마세요.

**① Claude 기다리게 하기** — 10-4 대로 tmux 안의 Claude 에게 "웹 지시 기다려줘" 라고 합니다. 한 번 해 두면 계속 기다립니다.

**② 터널을 열고 서버 켜기** — 내 컴퓨터 터미널에서 접속한 뒤,

```bash
ssh -L 8766:localhost:8765 <사용자 ID>@<HPC 로그인 주소>
```

접속한 **그 창에서** 서버를 켭니다.

```bash
devtrack serve            # --open 은 쓰지 않습니다 (HPC 에는 보통 브라우저가 없음)
```

- 터널은 이 ssh 가 접속한 로그인 노드로 이어집니다. 그래서 서버는 반드시 이 창에서 켜야 합니다. 다른 창은 다른 노드에 있을 수 있습니다.
- Claude 는 다른 노드의 tmux 에 있어도 됩니다. 둘 다 같은 기록 폴더를 공유 디스크에서 읽기 때문입니다.
- 앞의 `8766` 은 내 컴퓨터 쪽 번호입니다. 내 컴퓨터에서도 DevTrack 을 켜 두면 8765 를 쓰고 있어서 다른 번호를 씁니다.

**③ 웹 열기** — 내 컴퓨터 브라우저에서 `http://localhost:8766/` 을 엽니다. 오른쪽 위에 "실시간 · 로컬 서버" 가 보이면 웹에서 바로 저장되는 상태입니다.

**④ 지시 · 승인** — 메뉴의 **새 작업 지시**에서 지시를 등록합니다. 담당 AI 칸 아래에 "지금 웹 지시를 기다리는 AI: Claude (대기 모드)" 가 보이면 HPC 의 Claude 가 몇 초 안에 시작합니다.
진행 기록과 승인 요청도 이 웹에 나타나고, 승인 버튼을 누르면 바로 Claude 에게 전달됩니다.

**⑤ 끝내기** — 서버 창에서 `Ctrl+C`. ssh 접속이 끊겨도 서버는 함께 꺼집니다.
tmux 의 Claude 는 계속 기다리므로 다음에는 ②부터 다시 하면 됩니다. 서버가 꺼져 있는 동안에는 정적 웹([10-6](#/guide/s10-6))으로 보고, 지시 · 승인은 붙여 넣기로 합니다.

**알아 둘 점**
- **두 DevTrack 을 헷갈리지 않기:** 내 컴퓨터에서도 DevTrack 을 쓰면 `localhost:8765` 는 내 컴퓨터의, `localhost:8766` 은 HPC 의 DevTrack 입니다.
  둘 다 "Claude (대기 모드)" 로 보일 수 있으니 작업 목록으로 구분하세요. 지시는 일을 시킬 곳의 웹에서 합니다.
- **`Address already in use`:** 같은 노드에서 다른 사람이 8765 를 쓰고 있으면 서버가 켜지지 않습니다. `devtrack serve --port 8790` 처럼 다른 번호로 켜고 터널도 `-L 8766:localhost:8790` 으로 맞추세요.
  내 컴퓨터 쪽에서 같은 메시지가 나오면 앞의 `8766` 을 다른 번호로 바꾸세요.
- **`--open` 을 붙였을 때:** `xdg-open: no method available …` 같은 메시지가 길게 나옵니다. 브라우저를 띄우지 못했다는 뜻일 뿐 서버는 켜져 있습니다.

### 10-6. 정적 웹에서 달라지는 점

- **승인 · 지시는 붙여 넣기로:** 승인 · 메시지 · 새 작업 지시 · 완료로 처리 · 취소 · 삭제 버튼을 누르면 **Claude 에게 보낼 메시지**가 나옵니다.
  복사해서 HPC 의 Claude 대화(tmux 화면, 10-4)에 붙여 넣으세요.
- **웹 지시로 깨우기 불가:** 정적 웹은 기록을 쓸 수 없어서, 웹에서 보낸 지시로 기다리는 Claude 를 깨울 수 없습니다. 웹에서 바로 지시하려면 실시간 방식([10-5](#/guide/s10-5))을 켜세요.
- **⚠️ 공개 범위:** 공개 디렉토리의 내용은 주소를 아는 누구나 볼 수 있습니다. 코드 diff, 리포트, 로그, **발표 전 논문 원고 · 분석 그림**,
  PR 리뷰가 모두 포함됩니다. 비밀번호를 걸어 두세요 ([10-7](#/guide/s10-7)).
- **PDF · LaTeX:** 리뷰 리포트 PDF 는 Chrome 계열 브라우저가, 논문 컴파일은 TeX 가 있어야 만들어집니다.
  HPC 에 없으면 그 단계만 건너뛰고, Markdown 리포트와 원고는 그대로 보입니다.

### 10-7. 정적 웹에 비밀번호 걸기 (권장)

웹 공개 폴더는 주소를 아는 누구나 열 수 있습니다. 비밀번호를 걸면 사이트를 열 때 비밀번호를 묻고, 맞게 넣은 브라우저만 기록을 봅니다.

```bash
devtrack password            # 비밀번호 정하기 · 바꾸기 (8자 이상, 두 번 입력)
devtrack password --status   # 걸려 있는지 보기
devtrack password --off      # 풀기
```

- **한 번만 넣으면 됩니다:** 비밀번호를 넣은 브라우저는 쿠키 · 사이트 데이터를 지울 때까지 다시 묻지 않습니다.
  다른 사람과 같이 쓰는 컴퓨터에서는 다 본 뒤 사이드바 아래의 **잠그기** 를 누르세요.
- **바로 반영:** 공개 폴더(`devtrack config publish`)가 정해져 있으면 그 자리에서 반영됩니다. 없으면 다음 `devtrack publish --to <폴더>` 때 반영됩니다.
  비밀번호를 바꾸면 모든 브라우저에서 새 비밀번호를 다시 넣어야 합니다.
- **기록을 막는 것은 웹 서버입니다:** 화면만 가리는 것이 아니라, 비밀번호 없이 `data/` 의 파일 주소를 직접 열어도 403 이 나옵니다.
  공개 폴더의 `data/.htaccess` 를 Apache 웹 서버가 읽어서 막습니다. 비밀번호와 그것으로 만든 열쇠는 어디에도 저장하지 않고, 확인용 값만 남깁니다.
  실시간 방식의 `devtrack serve`([10-5](#/guide/s10-5))도 같은 비밀번호를 묻습니다. 그래서 같은 로그인 노드의 다른 사용자도 들어오지 못합니다.
- **`.htaccess` 를 읽지 않는 웹 서버**(nginx, GitHub Pages 등)에서는 `data/` 가 그대로 열려 있습니다. 이때는 사이트를 열면
  **비밀번호 보호가 동작하지 않음** 경고가 나옵니다. 데이터는 공개되어 있으니 다른 곳에 올리거나 실시간 방식으로 보세요.
- **DevTrack 을 업데이트한 뒤** 처음 거는 경우라면 `devtrack publish` 를 한 번 실행해 웹 화면 파일도 새로 복사하세요 ([10-1](#/guide/s10-1)).
- 공개 폴더에 `data/.htaccess` 가 이미 있으면(DevTrack 이 만든 파일이 아니면) 덮어쓰지 않고 멈춥니다. 그 파일을 옮긴 뒤 다시 실행하세요.

## 11. Codex 와 함께 쓰기 (선택)

Claude 와 Codex 를 함께 쓸 수 있습니다. 작업마다 **담당 AI** 를 정하면 그 AI 만 그 작업을 가져갑니다.

| 새 작업 지시의 "담당 AI" | 누가 처리하나 |
|---|---|
| Claude · Codex · Gemini | 고른 AI 만. 그 작업의 메시지 · 승인 결정 · 취소도 그 AI 에게만 갑니다 |
| 누구나 (먼저 시작한 AI) | 먼저 시작한 AI 가 맡고, 그때부터 그 AI 의 작업이 됩니다 |

다른 AI 의 작업을 대신 맡기려면 맡을 AI 에게 "T-0007 을 `--take` 로 가져와서 해줘" 라고 하세요
(`devtrack start T-0007 --take` — 담당 AI 가 바뀌고 기록에 남습니다).

### 11-1. Codex 설정 (한 번만)

**① 기록 규칙** — Codex 는 `~/.codex/AGENTS.md` 에 적힌 내용을 모든 대화에서 따릅니다. 아래 내용을 붙여 넣으세요
(5-1단계의 Claude 규칙과 거의 같고, Codex 에 맞게 몇 줄이 다릅니다). `~/devtrack` 부분은 2단계에서 받은 위치로 바꿉니다.

```markdown
## DevTrack 작업 기록 (Codex)
- DevTrack 에서 나는 "Codex" 다. `devtrack` 은 환경 변수 `DEVTRACK_AGENT=Codex` 로 실행한다
  (~/.codex/config.toml 의 `shell_environment_policy` 에 설정해 두었으면 따로 붙이지 않는다).
  `devtrack` 이 PATH 에 없으면 `~/devtrack/bin/devtrack` 을 쓴다. 규칙: ~/devtrack/docs/AGENT_PROTOCOL.md
- 의미 있는 작업(코드 변경, 코드 리뷰, 문서 리뷰, 데이터 분석, 논문, 시각화, 모델 개발, 브레인스토밍)은 `devtrack` 으로 기록한다. 간단한 질문 · 설명은 기록하지 않는다.
- 작업 시작 전과 각 단계 후 `devtrack inbox` 로 사용자 입력(새 지시, 메시지, 승인 결정)을 확인한다. 나에게 배정된 작업의 입력만 보인다.
- inbox 의 새 작업 지시 · 메시지(추가 질문 · 조사 요청)는 사용자에게 다시 묻지 않고 진행한다. 다른 작업 중이면 메시지는 지금 단계를 마친 뒤,
  새 작업은 지금 작업이 끝나거나 승인 대기가 되면 온 순서대로 처리하고 원래 작업으로 돌아온다. 메시지의 답은 그 작업에 기록하고
  (`devtrack log` · `devtrack artifact`) `devtrack inbox --task <TID> --ack` 로 처리 표시한다. 커밋 · 게시 등은 그대로 승인을 받는다.
- inbox 의 `[AI 메시지]` 는 다른 AI 가 보낸 것(리뷰 요청 · 리뷰 결과 등)이다. 같은 방식으로 처리하되 사용자 지시는 아니므로, 승인이 필요한 일은
  여전히 사용자 승인을 받는다. 리뷰받기로 한 작업(inbox 의 `끝나면 … 리뷰`)은 커밋 승인을 요청하기 전에 `devtrack review-request <TID>` 로 리뷰를 통과하고,
  심사받기로 한 논문(`끝나면 … 심사`)은 원고를 다 쓰면 심사를 요청해 지적대로 고치고 답변서(`--response`)와 함께 다시 요청한다.
  답변서는 열린 항목마다 `## R1 — 제목` 처럼 항목 ID 로 제목을 달아 질문에는 답을, 요청에는 고친 내용(고치지 않았다면 이유)을 쓰고,
  심사가 끝나 사용자에게 알릴 때는 심사 · 답변 기록(판정 메시지의 F-ID)을 `-a` 로 첨부한다.
- 논문 그림은 원고 옆 `figures/` 에 두고 원고에 `\graphicspath{{figures/}}`, 부를 때는 확장자 없이 `\includegraphics{fig_name}`.
  그림은 그 파일 이름 그대로 결과물로 올린다 (DevTrack 이 `tasks/<TID>/paper/` 에 원고 · 그림을 모은다).
- 사용자 결정이 필요하면 `devtrack request` 로 요청을 남기고 사용자에게 알린 뒤 멈춘다. `devtrack wait` · `devtrack inbox --wait` 로 오래 기다리지 않는다
  (웹에서 온 입력은 사용자가 터미널에 켜 둔 `devtrack watch --codex` 가 나를 다시 실행해 전달한다).
- 지시에 `/review-pr <URL>` 같은 스킬 호출이 있으면 `~/.codex/skills/<이름>/SKILL.md` 를 매번 새로 읽고 그 지침대로 진행한다.
- 의미 있는 단계마다 `devtrack step <TID> "지금 하는 일" -p <진행률>` 을 남긴다.
- 문제는 `devtrack issue`, 결과물은 `devtrack artifact` / 리뷰 리포트는 `devtrack review` 로 남긴다.
- 코드 리뷰 리포트는 개발자가 아닌 사람도 이해할 수 있게 쓴다: 한 줄 결론, 비개발자용 "한눈에 보기", 항목별 "쉽게 말하면", 용어 풀이.
- DevTrack 작업의 결과를 저장소에 반영할 때는 git commit/push 를 직접 하지 않고 `devtrack request <TID> "..." --commit -m "..."` 로
  승인을 요청하고, 승인되면 `devtrack apply <TID> <AID>` 로 반영한다. 단, 사용자가 채팅에서 직접 커밋 · 푸시를 지시하면 따른다.
- 사용자가 `[DevTrack 결정]` / `[DevTrack 메시지]` / `[DevTrack 새 작업 지시]` / `[DevTrack 작업 완료]` / `[DevTrack 작업 취소]` / `[DevTrack 작업 삭제]`
  메시지를 보내면 각각 `devtrack decide` / `devtrack comment` / `devtrack new` / `devtrack done --by-user` / `devtrack cancel` /
  `devtrack delete --yes` 로 먼저 기록한 뒤 진행한다.
- inbox 에 `[완료 처리]` · `[취소]` · `[삭제]` 가 오거나 도구 실행이 `⛔ DevTrack` 메시지로 막히면 그 작업은 즉시 멈추고, 안내대로 확인만 기록한 뒤
  (`devtrack inbox --task <TID> --ack`) 더 기록하지 않는다. 작업 삭제는 사용자가 요청하고 확인했을 때만 한다.
```

**② Codex 설정 파일** — `~/.codex/config.toml` 맨 아래에 추가합니다. `/Users/me/devtrack/data` 는 기록 폴더
(`devtrack config` 에 나오는 곳, 기본 `~/devtrack/data`)의 **전체 경로**로 바꿉니다.

```toml
[shell_environment_policy.set]
DEVTRACK_AGENT = "Codex"                        # Codex 의 기록은 "Codex" 이름으로

[sandbox_workspace_write]
writable_roots = ["/Users/me/devtrack/data"]    # 작업 폴더 밖에 있는 DevTrack 기록 폴더에 쓰기 허용
```

- 파일에 `[shell_environment_policy.set]` 이나 `[sandbox_workspace_write]` 줄이 **이미 있으면** 새로 쓰지 말고 그 아래에 한 줄씩만
  추가하세요. 같은 이름의 줄이 두 번 있으면 Codex 가 설정 파일을 읽지 못합니다.

- Codex 는 안전을 위해 작업 폴더 밖에는 쓰지 못합니다. 위 설정은 DevTrack 기록 폴더 한 곳만 쓰기를 허용합니다.
- 인터넷(`gh` · `git push`)은 Codex 대화창에서는 필요할 때 허락을 묻고, 웹 지시를 처리하는 `devtrack watch` 는 대화창이 없어
  물을 수 없으므로 실행할 때 인터넷을 허용합니다 (막으려면 `devtrack watch --codex --no-network`).

**③ 리뷰 스킬** (코드 · 문서 리뷰를 맡길 경우) — Claude 와 같은 파일을 링크합니다.

```bash
mkdir -p ~/.codex/skills/review-pr ~/.codex/skills/review-doc
ln -sf ~/devtrack/integrations/claude-skills/review-pr/SKILL.md ~/.codex/skills/review-pr/SKILL.md
ln -sf ~/devtrack/integrations/claude-skills/review-doc/SKILL.md ~/.codex/skills/review-doc/SKILL.md
```

**④ `codex` 명령** — 웹 지시를 받는 `devtrack watch` 가 Codex CLI 를 씁니다. 터미널의 `codex` 가 없으면 ChatGPT · Codex 앱,
VS Code 확장(원격 SSH 로 연 HPC 의 `~/.vscode-server` 포함)에 들어 있는 CLI 중 **가장 새 버전**을 자동으로 찾습니다 (오래된 CLI 는 새 모델을 쓰지 못합니다).
다른 것을 쓰려면 `export DEVTRACK_CODEX=<codex 경로>`. 어떤 CLI 를 쓰는지는 `devtrack watch` 를 켤 때 첫 줄에 표시됩니다.

**⑤ 작업 취소 바로 전달 (훅, 권장)** — Claude 의 5-4 와 같습니다. Codex 앱 · VS Code 에서 대화하며 일하는 Codex 가 작업 도중에
취소 · 삭제를 알 수 있게 합니다. `~/.codex/hooks.json` 을 만듭니다 (이미 있으면 `"PreToolUse"` 목록에 항목만 더하고,
`/Users/me/devtrack` 은 DevTrack 의 전체 경로로 바꿉니다).

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "hooks": [
          { "type": "command", "command": "/Users/me/devtrack/bin/devtrack-hook", "timeout": 10 }
        ]
      }
    ]
  }
}
```

- Codex 는 처음 보는 훅을 **사용자가 확인한 뒤에만** 실행합니다. Codex 앱의 **설정 → Hooks**(터미널 `codex` 에서는 `/hooks`)에서
  이 훅을 확인하고 신뢰로 표시하세요. 훅 내용을 바꾸면 다시 확인해야 합니다.
- `devtrack watch` 로 실행되는 Codex 는 훅 없이도 취소하면 바로 멈춥니다.

> 설정은 **새로 연 Codex 대화부터** 적용됩니다.

### 11-2. Codex 에게 작업 맡기기

**방법 A — Codex 채팅으로 지시.** Codex 앱(또는 터미널의 `codex`)에 평소처럼 지시하면 Codex 가 DevTrack 에 작업을 만들고 기록합니다.

**방법 B — 웹에서 지시 (`devtrack watch`).** Claude 의 대기 모드("웹 지시 기다려줘")는 Claude Code 의 기능이라,
Codex 는 대신 터미널에서 **실행기**를 켜 둡니다.

```bash
devtrack watch --codex
```

1. 웹의 **새 작업 지시** 에서 담당 AI 를 **Codex** 로 고르고 보냅니다.
2. 몇 초 안에 실행기가 Codex 를 실행해 작업을 처리합니다. 터미널 창에 무엇을 처리하는지 표시되고, 끝나면 Codex 의 요약이 진행 기록에 남습니다.
3. Codex 가 승인을 요청하고 끝나면, 웹에서 승인 · 수정 요청 · 메시지를 보낼 때마다 실행기가 Codex 를 다시 실행해 이어서 처리합니다.
   같은 작업은 같은 Codex 대화로 이어 가므로, 앞에서 읽고 한 일을 기억한 채로 처리합니다.

- 작업은 **대상 저장소 경로** 폴더에서 실행됩니다. 경로가 없는 작업은 `devtrack watch` 를 실행한 폴더에서 실행됩니다 (`--cwd 폴더` 로 바꿀 수 있음).
- 웹에서 작업을 취소 · 삭제하면 실행 중이던 Codex 를 바로 멈춥니다.
- 이 터미널 창은 열어 두세요 (멈추기: Ctrl+C). 다시 켜면 꺼져 있던 동안 들어온 지시부터 처리합니다.
- Codex 에 옵션을 더 주려면 `--` 뒤에 적습니다: `devtrack watch --codex -- -m <기본 모델>`.
  작업에 모델 · 추론 강도를 정해 두면 그 작업은 정한 모델로 실행합니다 ([6-1](#/guide/s6-1)).

## 12. 자주 묻는 질문 · 문제 해결

**웹에서 지시했는데 아무 일도 일어나지 않아요.**
먼저 작업 화면 위쪽의 표시를 보세요 (6단계): 담당 AI 가 기다리는 중인지, 아니면 깨워야 하는지와 그 방법이 나옵니다.
Claude 는 대화에서 말을 걸어야 움직입니다. 대기 모드("웹 지시 기다려줘")를 켜 두었는지, 그 VS Code 창이나 터미널이 열려 있는지 확인하세요.
터미널에서 띄워 두었다면 권한 확인 창이 떠서 기다리고 있지 않은지도 보세요 ([방법 C](#/guide/s6)).
아니면 Claude 채팅에 "devtrack inbox 확인하고 진행해줘" 라고 하세요. Codex 라면 `devtrack watch --codex` 가 켜져 있는지 확인하세요.

**Claude(또는 Codex)가 웹에서 지시한 작업을 가져가지 않아요.**
작업의 **담당 AI** 가 다른 AI 로 되어 있는지 보세요 (작업 화면 제목 아래 표시). AI 는 자기에게 배정된 작업만 가져갑니다.
`devtrack inbox --all-agents` 로 모든 AI 의 입력을 볼 수 있고, 대신 맡기려면 `devtrack start <작업 ID> --take` 입니다.

**웹에서 작업을 취소(또는 완료로 처리)했는데 AI 가 계속 일해요.**
대화 중인 AI 는 작업 단계가 끝날 때만 DevTrack 을 확인합니다. 훅(Claude 5-4, Codex 11단계 ⑤)을 설치하면 다음 명령 · 파일 수정
직전에 멈춥니다. 훅을 설치했는데도 계속하면 ① 훅을 설치한 뒤 **새로 연 대화**인지, ② Codex 라면 훅을 **신뢰로 표시**했는지 확인하세요.
AI 가 명령 없이 긴 답을 쓰는 동안에는 끼어들 수 없으니, 급하면 대화 창에서 직접 중지하세요.

**버튼을 누르면 메시지 복사 창이 떠요.**
정적 모드(오른쪽 위 "정적 · 읽기 전용")입니다. 메시지를 Claude 대화에 붙여 넣거나, 로컬에서는 `devtrack serve` 로 연 주소를 쓰세요.

**DevTrack 이나 스킬을 업데이트했는데 예전처럼 동작해요.**
이미 열려 있던 Claude 대화(대기 모드 대화 포함)는 예전 지침을 기억하고 있을 수 있습니다.
`git pull` 로 업데이트한 뒤에는 Claude 대화를 **새로 열고**, 필요하면 "웹 지시 기다려줘" 를 다시 말해 주세요.

**`devtrack: command not found`**
3단계의 PATH 설정을 확인하고, 터미널과 VS Code 를 다시 여세요.

**HPC 에서 `claude` 명령이 안 돼요.**
Claude Code 가 설치되지 않았거나 PATH 에 없는 경우입니다. [10-3](#/guide/s10-3) ① 을 따라 설치하고 `~/.local/bin` 을 PATH 에 넣으세요.

**HPC 에서 `devtrack serve --open` 을 하면 `xdg-open` 오류가 길게 나와요.**
HPC 에는 보통 브라우저가 없어서 띄우지 못했다는 뜻이고, 서버는 켜져 있습니다. 웹은 내 컴퓨터에서 SSH 터널로 엽니다 ([10-5](#/guide/s10-5)).

**HPC 터널 주소(`localhost:8766`)가 안 열려요.**
① `-L` 을 붙인 ssh 접속이 아직 열려 있는지, ② `devtrack serve` 를 **그 ssh 창에서** 켰는지 보세요.
다른 창에서 켠 서버는 다른 로그인 노드에 있을 수 있어 터널과 이어지지 않습니다 ([10-5](#/guide/s10-5)).

**웹 화면이 "불러오는 중"에서 멈추거나 이상해요.**
`devtrack serve` 를 실행한 터미널이 열려 있는지 확인하세요. DevTrack 을 업데이트(`git pull`)했다면 `devtrack serve` 를 껐다가 다시 켜세요.
정적 웹(HPC 의 웹 공개 폴더 등)이라면 `devtrack publish` 를 다시 실행한 뒤 브라우저에서 새로고침하세요 ([10-1](#/guide/s10-1)).

**예시 화면을 먼저 보고 싶어요.**
실제 기록과 섞이지 않게 별도 폴더에 예시를 만들어 엽니다.
```bash
devtrack --data ~/devtrack-demo demo
devtrack --data ~/devtrack-demo serve --port 8766 --open
```

**리뷰 리포트 PDF 가 안 만들어져요.**
PDF 는 컴퓨터에 설치된 Chrome(또는 Chromium · Edge)으로 만듭니다. 브라우저가 없으면 Markdown 리포트만 올라가고 활동 기록에 경고가 남습니다.
다른 위치에 설치했다면 `export DEVTRACK_CHROME=<브라우저 실행 파일 경로>` 를 지정하세요. 이미 올라온 리포트는 `devtrack pdf <리포트.md>` 로 따로 만들 수 있습니다.

**기록이 두 폴더에 나뉘어 쌓여요 (`DEVTRACK_DATA` 를 정했는데 `~/devtrack/data/` 에도 생겨요).**
`DEVTRACK_DATA` 같은 환경 변수는 그것을 정한 셸에서 켠 프로그램에만 전달됩니다. 다음 경우에는 그 변수를 몰라 기본 폴더에 기록합니다.
- 변수를 정하기 전에 켠 `devtrack serve` · `watch` · 대기 모드
- 다른 터미널 · tmux
- VS Code 에서 실행된 Claude 와 훅

`devtrack config data <기록 폴더>` 로 설정 파일에 정해 두면 어디서 실행하든 같은 곳을 씁니다. 그 뒤 켜 둔 `serve` · `watch` · 대기 모드를 다시 켜세요.
`devtrack config` 는 지금 쓰는 곳과, 다른 폴더에도 작업이 있는지 보여 줍니다. 그쪽 작업은 `devtrack --data <그 폴더> list` 로 볼 수 있습니다.

**기록은 어디에 있고, 백업은 어떻게 하나요?**
기록 폴더(`devtrack config` 로 확인, 기본 `~/devtrack/data/`)가 전부입니다. 이 폴더를 복사하면 백업이 됩니다.

**Claude 가 내 승인 없이 커밋할 수 있나요?**
DevTrack 작업은 승인된 요청(`devtrack apply`)으로만 커밋합니다. 승인한 diff 와 실제 변경이 다르면 실행을 거부합니다.
다만 채팅에서 직접 "커밋해줘" 라고 지시하면 그대로 따릅니다.

## 13. 명령 한눈에 보기

사용자가 직접 쓰는 명령:

| 명령 | 하는 일 |
|---|---|
| `devtrack serve --open` | 웹 대시보드 열기 (로컬) |
| `devtrack config` | 기록 폴더 · 웹 공개 폴더 보기. `config data <폴더>` · `config publish <폴더>` 로 정하고 `--unset` 으로 지움 (3단계, 10-1) |
| `devtrack publish` | 정적 웹으로 배포 (HPC 의 웹 공개 폴더 등) |
| `devtrack password` | 웹 비밀번호 정하기 · 바꾸기 (`--status` 확인, `--off` 풀기, 10-7) |
| `devtrack list` · `devtrack show T-0001` | 터미널에서 작업 목록 · 상세 보기 |
| `devtrack paper T-0005` | 논문 작업의 원고 폴더(`tasks/T-0005/paper`) 다시 만들기 · 빠진 그림 확인 (9. 논문 작성) |
| `devtrack watch --claude` | 웹에서 Claude 에게 온 지시를 작업마다 정한 모델로 처리 (6-1) |
| `devtrack watch --codex` | 웹에서 Codex 에게 온 지시를 Codex 로 처리 (11단계) |
| `devtrack model T-0001 opus-5.5 --effort xhigh` | 작업을 처리할 AI 모델 · 추론 강도 정하기 (`--clear` 해제, `--list` 고를 수 있는 모델 · 강도, 6-1) |
| `devtrack review-request T-0001 --reviewer Codex` | 지금 바뀐 코드(빌드 결과물 제외)를 다른 AI 에게 리뷰받기 — 결과는 [AI 메시지] 로 옴 (6-2) |
| `devtrack review-done T-0012 --verdict changes -m "…"` | (리뷰하는 AI) 이번 차례 결과 보내기: `approve` 통과 · `changes` 수정 필요. 논문 심사는 `accept` · `minor` · `major` · `reject` (6-3) |
| `devtrack review-request T-0005 --response response.md` | (논문) 고친 원고를 답변서와 함께 다시 심사받기 — 처음에는 `--doc 원고 --venue 저널` (6-3) |
| `devtrack send T-0012 "…"` | 다른 AI 가 맡은 작업에 메시지 보내기 ([AI 메시지]) |
| `devtrack --data <폴더> demo` | 예시 데이터 만들기 |

Claude 가 쓰는 명령 (참고): `new` 작업 생성 · `step` 지금 하는 일 · `issue` 문제 · `artifact` 결과물 · `review` 리뷰 리포트 · `text` Word · PDF 의 글자 뽑기 ·
`link` 작업 연결 · `latex` LaTeX 컴파일 (PDF 를 빌드로 기록) ·
`request` 승인 요청 · `apply` 승인된 커밋 실행 · `inbox` 사용자 입력 확인 (자기에게 배정된 작업만) ·
`start --take` 다른 AI 의 작업 가져오기 · `done` 완료 · `hook` 취소 · 삭제를 일하는 중인 AI 에 전달 (5-4).
전체 설명은 `devtrack --help` 와 [에이전트 규칙](https://github.com/hyungyukang/DevTrack/blob/main/docs/AGENT_PROTOCOL.md)을 보세요.
